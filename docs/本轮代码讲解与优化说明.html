2.1 confidence.mjs134 行 · 纯函数库

主要功能 计算二项比例的精确置信区间（Clopper-Pearson）。导出 5 个函数： betai（正则化不完全 Beta）、cpInterval（双侧）、 cpUpper / cpLower（单侧）、rateWithCI（一次算全）。
执行流程 三层递进，自底向上：
  1. lgamma（Lanczos 近似 + 反射公式）—— 求 log Γ，避免大阶乘溢出
  2. betacf + betai —— 连分式求正则化不完全 Beta 函数 Ix(a,b)
  3. solveBeta（二分求根）+ cpInterval —— 反解出置信区间端点
调用 cpUpper(k, n, α) 时，若 k=0 走闭式 1 − α^(1/n)，否则走二分。
关键实现 ① 为什么不用正态近似。我们的样本量不大（n 最小为 18），且大量情形是 k=0——正态近似 在 p̂=0 处会退化成"区间宽度为 0"，得出"误报率必然是零"的荒谬结论。Clopper-Pearson 是精确方法， 在 k=0 时仍给出正的上界（这正是我们要的）。
② 为什么"保守"是优点。Clopper-Pearson 的区间比 Wilson 等近似方法略宽。 对我们来说这恰好正确——宁可高估风险，不低估。
③ k=0 与 k=n 的闭式。这两种极端情形二分法也能解，但闭式更快且无误差累积。 注意此处有个坑：双侧区间必须用 α/2 而不是 α（见下方"已修的 bug"）。
设计意图与优点
  1. 零依赖。只用 Math，与整个内核的"自包含"取向一致——这样它既能被 Node 调用，也能被内联进插件。
  2. 分层清晰。数学函数（lgamma / betacf / betai）与业务函数（cpInterval / rateWithCI）分离，前者可独立测试。
  3. 可核验。纯函数、无状态，因此可以用完全独立的实现（Python scipy）逐组对拍——实际也这么做了。
  4. 导出了"单侧"与"双侧"两套接口。我们的场景（"至多这么高"）用单侧，但双侧留着以备他人复用。
优化建议
  1. 命名易混（建议优先）。rateWithCI() 的返回值同时含 upper/lower（单侧）与 ci: {lo, hi}（双侧）， 两者语义不同却名字相近。建议改为 oneSidedUpper / twoSided。
  2. 缺大参数的验证。Lanczos 近似在 a+b 很大时（如 1000 以上）精度未验证， 而对拍用例最大只到 n=402。建议补一组大参数用例。
  3. 二分迭代上限写死 200 次。可接受（微秒级），但建议加一句注释说明"200 次足以到机器精度"， 否则读者会怀疑是否够用。
  4. betai 会抛错但缺 @throws 标注。x 不在 [0,1] 时抛异常， JSDoc 里应写明。
  5. solveBeta 未校验 target 落在 (0,1)。传入 0 或 1 会得到边界值而非报错—— 建议加断言。
这个文件里已经修掉的一个真 bug（值得记录）
cpInterval 的 k=0 / k=n 分支最初写成了 1 − α^(1/n)， 但双侧区间应该用 α/2。结果 n=20,k=0 算出 0.139108（单侧值）， 而公认值是 0.168433。
是靠对拍测试发现的——自己跑自己的话，这个错误会一直藏着。

2.2 orbital-elements.mjs150 行 · 纯函数库

主要功能 经典轨道要素与惯性系位置速度之间的双向转换，外加一组向量工具。 导出 12 个符号：6 个向量运算（vsub/vadd/vmul/vdot/vcross/vnorm）、 solveKepler、elementsToState、stateToElements、 deg/rad/vdiff。
执行流程 正向（elementsToState）： 
M ──牛顿迭代──▶ E ──▶ 近焦点系 (x_pf, y_pf) 与速度
                      │
                      └──正交旋转 R(ω, i, Ω)──▶ 惯性系 (x, y, z)
反向（stateToElements）：由 r、v 算 h、n、e 向量 → 套标准公式取角度 → 真近点角 ν 折算回平近点角 M。
关键实现 ① 牛顿迭代的初值。E₀ = M + e·sin M（Danby 建议）。对 e 接近 1 的情形， 常规初值 E₀ = M 会收敛很慢甚至发散，这个初值把迭代次数压到个位数。
② 旋转矩阵只展开两列。近焦点系的 z 分量恒为 0，所以旋转时只需 R 的前两列， 省掉 1/3 的乘法——这是"知道问题结构"带来的简化。
③ 反向时逐步夹逼反余弦参数。Math.acos 在 |x|>1 时返回 NaN， 浮点误差常让 h_z/h 变成 1.0000000000000002，所以每处都套了 Math.max(-1, Math.min(1, ...))。
设计意图与优点
  1. 补齐了内核真正缺的那一块。内核的状态量是轨道平面内的二维坐标， 而所有外部基准（Orekit、教材）都以三维要素给输入输出。没有这个转换层，就无法与外部对话。
  2. 刻意做成独立模块、不依赖内核。这样它可以用在任意上下文里， 也让"与 Orekit 对拍"成为对本文件的独立检验。
  3. 角度单位统一用弧度并在文件头声明。教材给的是度数，转换错误是这类代码最常见的 bug—— 显式约定 + 提供 deg/rad 工具函数，是有效的防呆。
  4. 反向转换存在，使自检闭环成立。要素 → 状态 → 要素 应当回到原值， 这在验收里是一条独立的断言。
优化建议
  1. ★ solveKepler 缺 e 的范围校验（边界情况，建议优先）。 该函数对 e ≥ 1（抛物线/双曲线轨道）会静默给出错误结果—— 牛顿迭代在 e>1 时公式形式不同（要用双曲开普勒方程）。 而内核的 makeScenario 是明确拒绝 e≥1 的，两处行为不一致。 建议在这里同样抛出明确错误，或至少加注释说明适用范围。
  2. ★ solveKepler 与内核的 K.solveKepler 是两份实现。 目前二者都能用，但将来改一处忘另一处就会漂移。 两条路：
    （a）本模块改为复用内核的——但会引入耦合，与"独立模块"的设计意图冲突；
    （b）保持独立，但加一条"两者结果一致"的断言——推荐这条，既保留独立性又防漂移。
  3. stateToElements 在 e→0 时退化未说明。近圆轨道下 argp 与 raan 在数学上不唯一（节点线不定）， 当前会返回接近随机的值。建议加注释，或在 e 小于阈值时标记为"未定义"。
  4. 导出的向量工具偏多而少用。12 个导出中， vadd/vmul/vdiff 在本项目里几乎没被用到。 可以考虑精简，或明确标注"供外部复用"。

2.3 test-confidence.mjs164 行 · 验收脚本

主要功能 对 confidence.mjs 做 5 组共 25 项断言，其中关键一组是 与 Python scipy 逐组对拍（11 个测试点）。
执行流程 
读 reference.json（scipy 生成）
  ├─ 1) 11 组 (k,n) 对拍：lo / hi / 单侧上界   ← 外部参照
  ├─ 2) k=0 闭式核对（5 组）                  ← 内部一致性
  ├─ 3) 经典公认值（3 组，如 n=20,k=0→0.168433）
  ├─ 4) 结构性质：对称性 / 单调性 / 区间包住点估计 / α 单调
  └─ 5) 打印本次报告要用的实际数字（8 行）
最后按 fail 计数决定退出码。
关键实现 ① 参照值来自完全独立的实现。JSON 由 Python scipy.stats.beta.ppf 生成， 与 JS 实现没有任何共享代码——这是"对拍"能成立的前提。
② 五类断言分层。外部参照（最强）、闭式（次强）、公认值、结构性质（不依赖任何参照，纯自查）、 输出核对。即使外部参照文件丢了，后三类仍能跑。
③ 结构性质是"免费的"验证。对称性 lo(k,n) = 1 − hi(n−k,n) 这类恒等式不需要任何外部数据就能检验实现是否自洽——是很划算的一层。
④ 抓到了真 bug。第 3 组（公认值）一开始就红了：n=20,k=0 给出 0.139108 而非 0.168433。 根因是 cpInterval 双侧分支误用了 α。
设计意图与优点
  1. 测试不是"跑一遍看有没有报错"，而是与独立实现比对数值。这是"验证"与"冒烟"的区别。
  2. 容差 1e-9 与实测偏差 5.55e-16 之间留了 7 个数量级余量。 既能抓住真实错误，又不会因浮点抖动误报。
  3. 失败时输出实际值与期望值对照（不是只说"不相等"），便于定位。
  4. 末尾直接打印报告要用的数字——把"验证"和"产出材料"连起来，避免手抄出错。
优化建议
  1. 参照文件缺失时的处理不够友好。当前若 confidence-reference.json 不存在， 直接 exit(1)，但没有告诉使用者怎么重新生成它。 建议在错误信息里附上那行 Python 命令。
  2. 验证词/断言数的呈现可以更明确。"25 项"是人工数出来的； 建议脚本自己在末尾打印 通过 N 项（已有）并在 README 里引用这个数字。
  3. 容差对所有测试点统一为 1e-9，但 k=0 走闭式、理论上更精确（实测偏差 1e-16）。 可以对两类分别设容差，让"闭式精确"这一点显式化。
  4. 对照组可以再扩。当前最大 n=402；补几组大 n（如 2000、10000）能覆盖 lgamma 的大参数区间。

2.4 test-external-benchmark.mjs194 行 · 验收脚本

主要功能 把实现与两个第三方公开发布的基准对拍：
① Orekit 官方测试 KeplerianOrbitTest.testKeplerianToCartesian（期望值 15 位有效数字）
② Curtis 教材 Example 2.3（最大/最小高度、远地点速度）
共 8 项断言。
执行流程 第 ① 组（要素→状态）： 
输入 6 个要素 + μ
  ├─ 用【内核的】K.solveKepler 求 E       ← 刻意调用内核，才能测到它
  ├─ 标准公式算近焦点系位置速度
  ├─ 正交旋转到惯性系（R(ω,i,Ω)）
  ├─ 与 Orekit 期望值逐位比对
  └─ 自动探测 μ：试两个候选，报告更匹配的那个
另加一条：内核 solveKepler 的残差 |E − e·sinE − M|
第 ② 组（Curtis）：由 r₀,v₀ 反推 a,e → 用内核构造等价场景 → 扫一圈找最近/最远点 → 与教材答案和解析式 a(1+e) 双重核对。
第 ③ 组：只打印说明，不做断言——解释为何这一组不列为对拍项。
关键实现 ① 刻意调用内核的 solveKepler 而非自己写一份。这一个选择决定了测试"测的是谁"—— 如果用自己的实现，测的就是这个测试脚本，而不是作品。
② 自动探测 μ。Orekit 测试文件里没有直接写出 μ（它来自基类）， 于是把两个候选值都试一遍，用"哪个偏差更小"反推。实测 3.9860047e14 给出 1.2e-15、 另一个给出 3.6e-8，差 7 个数量级，判定毫无歧义。
③ 对"教材数字对不上"的处理方式。Curtis 教材的最大高度是 9560 km，我们算出 9572.5 km。 这里没有直接改容差放过去，而是：先用解析式 a(1+e) 独立复核， 再核对教材另给的远地点速度（4.39 km/s，与我们一致），最后判断差异来自教材取整。 把"对不上"变成一个可解释的结论，而不是掩盖。
④ 第 ③ 组只写说明、不做断言。这一组本可以对拍（Orekit 传播教程）， 但教程输入含倾角而内核是平面问题，若先做投影再比对，那一步会引入自己的实现， 说服力反而下降。于是选择"不做，并说清为什么"。
设计意图与优点
  1. 补上了此前最缺的一环：外部参照。在此之前所有证据都是"自己写的解析解 vs 自己写的积分器"， 属于内部自洽；这一组才是"和行业公认实现比"。
  2. 选基准的眼光。Orekit 的期望值是源码里硬编码的常量（非运行时计算）， 作为独立参照的可信度最高。
  3. 坦白边界。文档与脚本里都写明"本文对拍的是解析解 + 要素转换，不是数值积分器"， 不越界声称。
优化建议
  1. ★ 期望值的存放方式与 test-confidence 不一致（结构问题，建议优先）。 本文件把 15 位有效数字直接写在代码里，而 test-confidence.mjs 放在外部 JSON。 抄录 15 位数字很容易出错（少一位、记错符号），且出错后测试会变成"错的基准"。 建议统一成外部数据文件，并在文件头注明来源 URL。
  2. μ 的自动探测可以更明确。当前逻辑是"排序取最优"，建议同时打印"两个候选的偏差比"， 让"判定有多确定"一目了然（现在是隐含的）。
  3. 第 ② 组的容差 20 km 是经验值。虽然注释里说明了理由， 但更严谨的做法是：用解析式 a(1+e) 作为主判定（可精确核对）， 教材数字仅作参考——实际上第 ② 组已经这么做了，可以把教材值降为"参考"标注。
  4. 可以补一条"跨实现"的断言。既然 orbital-elements.mjs 与内核都有 solveKepler，可以在这里加一条两者结果一致的断言，顺带解决 2.2 里提到的漂移风险。

2.5 integrator-guide.mjs150 行 · 生成器

主要功能 生成《积分器选用参考表》——回答"给定任务和精度，该选哪个方法、每圈要多少步"。 输出到屏幕并写入 out/integrator-guide.txt。
执行流程 
遍历 3 档精度 × 4 个场景 × 5 种方法 = 60 个组合
  └─ 每个组合调用内核 calibrateStep(targetPosErrKm = 相对值 × a)
       ├─ calibrationReliable=false → 记「不可预测」
       ├─ requiredStepsPerOrbitPos=null → 记「—」
       ├─ feasiblePos=false → 记数字 + 星号（超搜索上限）
       └─ 否则 → 记数字
→ 输出三张表（每档精度一张）+ 决策流程 + 陷阱说明
关键实现 ① 数据全部现场标定，没有一个经验值。这是本文件最重要的设计决定： 表格里的每个数字都来自 calibrateStep， 与 orbit_calibrate_step 工具用的是同一套标定逻辑。 好处有二：一是随内核自动更新，不会出现"文档写 400 步、实际要 500 步"； 二是智能体在会话里给出的建议与这张表同源，不会互相打架。
② 三档精度用"相对轨道尺度"表述。targetPosErrKm = 相对值 × 半长轴。 若用绝对值（如"1 km"），大轨道会显得容易达标，横向比较失去意义。
③ 三种标记承载三种不同的"我不知道"。 不可预测（误差非幂律）/ —（位置口径不可靠）/ *（超搜索上限）， 各自对应工具的不同拒答理由。这一层语义是刻意保留的。
④ 档位选择的教训写进了注释。第一版用 1e-9，结果 LEO 只需 7 mm， 导致全表几乎都是"不可达"——表格信息量反而下降。改成 1e-6/1e-8/1e-10 后才有区分度。
设计意图与优点
  1. 把"选型"从口头经验变成可复现的产物。没有它，使用者只能猜"该用多少步"。
  2. 表格里的空格是设计而非缺陷。文件里保留了工具"拒绝给数"的三种情形—— 这比填上假数字更有价值，也与项目"宁可说不可用"的一贯取向一致。
  3. 与内核同源。避免了"文档与工具说法不一"这类最伤信任的问题。
优化建议
  1. ★ TRAITS 表里"稳定性"一列是手写的定性描述，非实测（可读性问题）。 表格其余部分都是实测数据，唯独这一列是人工判断——混在一起容易让读者以为它也是实测的。 建议加注"定性描述"，或干脆把这一列移出实测表格。
  2. 三种标记的含义只在文档里解释，代码里没有注释。 * 的含义（超搜索上限）尤其容易被阅读代码的人误解为"错误"。 建议在生成逻辑处加一行注释。
  3. TARGETS 档位的选取依据只写在文档里。 建议在代码注释里也留一句（"第一版用 1e-9 导致表格无区分度，故改为三档"）， 否则后来者可能又改回 1e-9。
  4. 可以输出 --json。当前只有人读的文本格式， 若能让机器读，就能被 verify-all 或其他工具消费。

2.6 verify-all.mjs / .ps1 / .cmd146 / 99 / 100 行 · 编排

主要功能 一条命令跑完全部验收项并汇总结果。做成三种形态以适配不同环境。
执行流程 
读参数（--full 含慢项 / --json 机器可读）
→ 依次运行 8 个（或 10 个）脚本
    ├─ 记录退出码与耗时
    └─ 从输出里抓「通过 N 项」摘要（正则，失败不影响结果）
→ 打印总表 + 失败清单 + 退出码
关键实现 ① 三种形态是环境逼出来的。本机沙箱下 spawnSync 报 EBUSY——连 cmd.exe 都起不来，说明该环境禁止一切子进程。 Node 版功能最全（有 --json、耗时、摘要）， .ps1 / .cmd 版由 shell 自己串行，不依赖 spawn。
② 退出码语义正确。全部通过才 0，任一失败即 1——这样才能被 CI 或上层脚本判定。
③ 摘要提取用"尽力而为"策略。正则匹配不到摘要不报错，只少显示一行—— 不让"锦上添花的信息"影响"核心结论"。
④ 脚本清单同时出现在三个文件里（各形态一份）。这是当前的显式重复（见优化建议）。
设计意图与优点
  1. 降低"愿意自己验一遍"的门槛。评委或队友不用逐个敲 10 条命令—— 这是决定他们会不会真去验证的关键。
  2. 区分快慢两集。默认只跑快速集（约 10 秒），慢项要显式加 --full。 避免"第一次体验就要等几分钟"。
  3. 跨环境可用。三种形态覆盖了正常终端、受限环境、纯批处理三种场景。
优化建议
  1. ★ 脚本清单在三处重复（结构问题，建议优先）。 .mjs、.ps1、.cmd 各维护一份清单， 新增一个验收脚本要改三处——这正是本项目已经反复踩过的"清单漏更新"陷阱。 建议：用一个 suites.json 作为单一来源，三份脚本都读它 （.cmd 读 JSON 稍麻烦，可退化为读一个纯文本清单）。
  2. .mjs 里应提示 spawn 可能失败。当前 EBUSY 时只报"未通过"， 使用者不知道"换个形态就能跑"。建议检测到 r.error 时打印 "当前环境的子进程受限，请改用同目录的 verify-all.ps1"。
  3. 超时 900 秒是硬编码。慢项（网格统计）在慢机器上可能超。 建议参数化为 --timeout。
  4. --json 的 schema 未文档化。既然提供了机器可读输出， 应在文件头用注释写明字段含义。
  5. 可以并行化。快速集 8 项互相独立，理论上可并行（Node 有 worker_threads）。 但当前总耗时 7.4 秒，收益有限，优先级低。

2.7 grid-eval.mjs 的两处修改434 行 · 已有工具

改了什么 ① 新增置信区间输出段（在跨场景汇总之后），输出 95% / 99% 两档单侧上界， 分误报、漏报两组。
② 新增 emit helper：(s) => { console.log(s); lines.push(s) }， 让新加的输出同时进屏幕和留档文件。
③ 把 const lines = [] 的声明提前到 emit 之前（修 TDZ 错误）。
为什么改 ③ 是为了 ②，② 是为了 ①——一个连锁的修正链：
原本 lines 声明在文件末尾附近（只为"把汇总表写进文件"服务）。 加入置信区间时我用了 console.log，结果屏幕上能看到、写进 out/grid-eval.txt 却没有。 改用 emit 后触发 Cannot access 'lines' before initialization—— 因为声明在调用之后，撞上了 const 的暂时性死区。于是把声明提前。
设计意图与优点
  1. emit 这个抽象是对的。"同时写屏幕和文件"是一个真实的重复需求， 抽成一个 helper 后，新增输出不会再漏掉一半。
  2. 改动局限在输出层，没有触碰计算逻辑——统计口径本身未变，风险可控。
  3. 顺带暴露了流程缺口：语法检查（--check）全过， 只有真跑一遍看退出码才发现 TDZ 错误。这强化了"必须实跑验证"的纪律。
优化建议
  1. ★ 其他脚本可能有同样的"屏幕有、文件没有"问题（建议优先排查）。 emit 只在 grid-eval.mjs 里有。 建议扫一遍所有写留档的脚本（loop-runner、diagnose 等）， 确认"屏幕输出"与"文件留档"内容一致。这次就是靠交叉检查才发现 grid-eval 的缺口。
  2. 把 lines + emit 抽成小工具模块。 既然多个脚本都需要，可以做成 log-util.mjs，导出 makeEmitter()，一次性解决"声明位置"和"重复实现"两个问题。
  3. emit 定义在模块中部，位置不显眼。 建议移到文件头部的工具区，或加注释说明"为什么这个声明必须靠前"（TDZ 容易再犯）。

2.8 loop-runner.mjs 的参数修正474 行 · 已有工具

改了什么 迁移场景 GOAL_D 的偏心率从 0.6 改为 0.45， 并加了三行注释说明为什么。计算逻辑一行未动。
连带效果：该目标的实测步数从 12003 步降到 5162 步。
为什么改 原参数物理上不成立。a = 12000 km、e = 0.6 对应的近地点地心距是 12000 × (1 − 0.6) = 4800 km，低于地球半径 6371 km——轨道在地球内部。
发现途径不是人眼检查：是在给内核加上"近地点必须高于地表"的物理校验之后， grid-eval.mjs 直接跑不动了（它用的正是这个场景被新校验拦下），顺着报错追下去才发现的。
设计意图与优点
  1. 换成 0.45 比原来更严苛。近地点地心距 6600 km（高度仅 229 km）， 比原来"更难的题"——这不是降低标准，而是换成物理上成立且更严格的题。
  2. 注释写清了来龙去脉（原值是什么、为什么错、新值怎么选的）， 后来者不会再改回去。
  3. 这次修正本身就是"验证严谨性"的证据：我们不仅检查数值方法， 还会检查测试用例本身是否成立，而且是自查发现的。
优化建议
  1. ★ loop-runner.mjs 不写留档文件（可维护性问题）。 out/loop-runner.txt 一直靠人工重定向生成， 这也是它长期停留在旧内容（10-01 的 e=0.6 数据）而没人发现的原因。 建议像 grid-eval 那样自己写 out/。
  2. 参数分散在多个 GOAL_ 常量里，没有集中校验。 既然内核已有物理校验，建议在脚本启动时一次性把所有目标过一遍校验， 出问题时立刻报错，而不是跑到中途才失败。
  3. 可以把"迁移场景"的参数提成配置文件。 这类场景会随覆盖范围调整（我们已经从 5 个加到 6 个）， 集中在配置里比散在代码里更好维护。
