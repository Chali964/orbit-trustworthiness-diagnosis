需要警惕的不是"撞车"，而是叙事撞车："用 LLM 智能体编排科学计算工作流"这个故事已被占位—— Foam-Agent（334 stars，已发 CMAME 论文）做的是 CFD 自动化，Amy（6 stars）做的与我们的功能最接近。 建议 把差异化重心从"用智能体做验证"移到「判断可审计」与「误差预算」——这两点目前无人做得扎实。

（二）可借鉴项（三个具体建议）

来源可借鉴什么对我们的具体价值
audit-loop
明确指出"AI 自我检查是结构性失败"		 它给出的失败模式清单：refinement-aware bias、CoT trust、sycophancy、self-preference bias、intrinsic self-correction 反而降低准确率（引 Huang et al., ICLR 2024） 可为我们的"判断可审计"提供理论依据。我们的做法（用确定性规则核对，不让模型自审）正好符合它给出的"唯一结构上可行"的路径。答辩时引用这条会让元层验证更有分量
astroworld 误差残差归因：RTN 分解（径向/切向/法向）+ FFT 频谱识别隐藏信号 我们的误差预算是按误差机制分解，它按空间方向分解。两者互补——若在答辩中提到"可扩展到方向分解"，是加分点，但当前不必实现
DiffEqDevTools.jl analyticless_test_convergence：无解析解时改用高精度参考解做收敛测试 我们的场景有解析解（开普勒），所以不需要。但这个方法提示了一条推广路径：将来做 J2 摄动时，解析解消失，可改用高精度参考解做观察阶测试——这正好回应"只支持二体"的质疑

（三）存在冲突或风险的部分

风险 1（叙事撞车）：「用智能体编排科学计算」已被占位 Foam-Agent 334 stars、已发 CMAME 论文，其定位就是"LLM 多智能体自动化科学计算工作流"。
后果：如果我们的答辩把"用智能体做科学计算自动化"当主要卖点，评委会问"这和 Foam-Agent 有什么区别"。
应对：差异化必须落在「验证对象是数值方法本身」+「判断可审计」+「误差预算」这三点上，而不是"我们也在用智能体做科学计算"。
风险 2（方法不新）：收敛阶测试是成熟方法 test_convergence 在 SciML/DiffEqDevTools.jl（53 stars）中已是标准功能， compute-physics-benchmarks、OrbitLab 等多个项目也做积分器阶数对比。
后果：不能把"做了观察阶测试"说成创新。我们在项目文档里已经写明"方法层是成熟学科"，这个处理是对的，继续保持。
风险 3（生态位观察） AGH 官方 skills 库 62 stars，第三方插件（dsh-tool-agnes 1★、agnes-media 3★）都是媒体生成类。 科学计算类插件在 AGH 生态里目前是空白——这既是机会（无人占位），也说明生态尚不成熟，评审时不宜把"AGH 生态丰富"当卖点。

五结论建议

技术选型：不需要调整 AGH 是赛事指定的运行底座，Agnes 模型是赛事指定的模型——这不是技术偏好问题，没有替代方案。
内核用 JavaScript 也是被 AGH 逼出来的（其 Python 运行时 runtime.python.execution 仍为 stub），属合理约束。
结论：维持现状。
功能定位：建议微调三处 ① 卖点重心从"智能体做验证"移到"判断可审计 + 误差预算"。
理由：前者已被 Foam-Agent（334★，已发论文）与 Amy 占位；后者在本次检索中未找到做得扎实的后继者。
② 把"判断可审计"提到与内核同等的位置。
理由：它与 AGH 官方技术报告自称的 “evidence-first agent runtime” 方向一致（是加分而非独创），但同类项目 （audit-loop、agent-receipts）star 数都是 0、明显未完成工程化——我们做得更完整。
③ 引用 audit-loop 的文献来支撑审计设计。
理由："模型自审结构性失败"有论文支撑（refinement-aware bias、CoT trust、sycophancy 等），引它能让我们的做法从"我们想的"变成"有依据的"。
★ 查重本身的局限（必须说明） ① 未做代码级检索。WebSearch 不支持 GitHub 代码片段搜索（use code search 语法），本次仅覆盖仓库名、README 描述与间接标签。可能漏掉"代码里实现但 README 没写"的项目。
② 未遍历 GitHub 全部 topic 页。topics 维度仅通过检索式间接覆盖。
③ 相似度评级是人工判断，基于 README 与技术描述的语义比对，未做代码相似度计算。
④ 检索偏向英文结果，中文项目与国内平台（Gitee 等）未纳入本次范围。
检索方法：5 轮 WebSearch（约 20 组关键词，覆盖功能同义词 / 技术方法词 / 技术栈组合 / 场景判据四个方向）， 命中相关项目 18 个；对其中 17 个通过 GitHub REST API 核实 star / fork / 语言 / 最近推送时间。
数据准确性：star 数以 API 实时值为准。注意搜索引擎缓存的 star 数可能严重失真（本报告即发现某项目缓存值 3434、实际 43）。
结论档位：「未发现功能重复实现」这一结论基于上述检索范围，不等于全网不存在——代码级检索与中文平台的盲区已列于第五节。
