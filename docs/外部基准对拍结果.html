二基准一：Orekit 官方测试套件

2.1 为什么选它

Orekit 是欧洲空间局生态中广泛使用的开源航天动力学库，其官方测试套件里的期望值是逐位写在源码里的硬编码常量—— 不是运行时算出来的，而是开发时确定的。这使它们成为理想的独立参照。

关于「最大高度相差 12.5 km」
远地点速度更能说明问题：教材给 4.39 km/s，本实现 4.3886 km/s——若真如教材所写 r_max 对应 15938 km， 速度应为 4.3920 km/s。两者四舍五入都是 4.39，所以速度这个量对不出差异。

而本实现的最大高度可由解析式独立复核：r_max = a(1+e) = 12975.2604 × 1.2293026 = 15950.52 km， 对应高度 9572.52 km。数值扫描结果与解析式一致到 1e-6，说明本实现内部自洽。
教材取 4 位有效数字，此处差异更可能来自教材取整或其积分器步长带来的偏差。

四一组刻意没做的对拍（以及为什么）

Orekit 官方传播教程（固定步长 RK4，10 s，传播 6000 s）为何未列为对拍项
该教程的初始条件含 倾角 i = 7°，而本内核的状态量是轨道平面内的二维坐标（nq = 2）。

这不是能力缺失——任何二体轨道都在一个平面内，平面内运动加上一次旋转就与三维完全等价 （第 ② 节的对拍正是这么做的）。

但若要做这组对拍，必须先把初始状态投影到轨道平面，那一步会引入我们自己的实现—— 于是对拍结果将不再纯粹反映内核，说服力反而下降。故不列为对拍项，并在此说明理由。

五答辩话术

你们的实现怎么证明是对的？
「分两类证据。

一类是内部自洽：解析解与数值解对拍、收敛阶实测、守恒量检验，加上约 480 个配置单元的误报漏报统计。

另一类是外部一致——这是更缺的一环：我们把同样的输入喂给我们的实现，看输出是否与行业公认的实现相同。
对照 Orekit 官方测试套件里逐位写死的期望值，位置和速度的相对偏差都是 1.2×10⁻¹⁵—— 这已经是双精度浮点的极限，逐位相同。
另外对照 Curtis 教材的一道标准例题，最小高度、远地点速度都吻合。

要说清边界：这两组对拍走的是解析路径，验证的是要素转换与解析解； 数值积分器本身由收敛阶测试和逐点误差另外覆盖。」
为什么你们自己写转换，而不是直接用 Orekit？
「两个原因。

第一是运行环境：Orekit 是 Java 库，而本作品要作为 AGH 的后端插件运行在 Node 环境里， 自包含、零外部依赖是它能被智能体直接调用的前提。

第二，也是更重要的——自己写才需要外部对拍。 如果我们直接用 Orekit，那"实现是否正确"就成了对 Orekit 的信任问题； 现在我们自己实现，并且用 Orekit 的期望值把它验证到浮点极限， 这恰好构成了一个完整的验证闭环。」
